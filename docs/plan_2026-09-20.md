# 改进方案与已排队的训练（2026-09-20）

> 用户指令："根据现在的情况分析改进思路，然后排好模型训练"
> 本文是决策记录：**现状 → 为什么这么改 → 排了什么**。数字出处见
> `docs/queue_results_2026-09-20.md`（同一协议：64 env / 20 s / 冻结命令 / 同一物理）。

## 1. 现状：三个已确证的事实

**事实 1 — 我们加的那 12 个偏差开关是同口径下最差的一族。**
（ALIGN_OFF = 全部偏差关 = 官方配方；HEAD = 官方配方 + 头块）

| 配方 | 走动环境 | 走动 med\|Δψ\| | 净速度 | 站立（零命令） |
|---|---|---|---|---|
| 官方配方 verbatim（align_official） | 7/64 | 405.6° | 0.00 | — |
| **官方配方 + 头块**（align_full / align_fwd） | 24 / **51**/64 | **64.2° / 64.3°** | 0.00 / **0.118** | 0 摔 |
| ck7000（我们的旧配方，无头块） | 49/64 | 90.7° | 0.089 | 1 次 reset |
| 我们 12 偏差 + 头块（ours_head ×3） | 18–30/64 | **383.6 / 389.6 / 452.1°** | ≈0.05 | **62–64 次 reset** |
| 我们 12 偏差 + 头块 + 站立项（ours_stance） | — | 213.1° | 0.034 | **55 次 reset / 离地 86 mm** |

→ 官方配方 + 头块在**每一条轴上都更好**：更直（64° vs 384–452°）、更快（0.118 vs 0.05 m/s）、
站得住（1 次 vs 55–64 次）。而且它正是用户一开始要求的"对齐官方"那一族。
→ 但**官方配方 verbatim 只有 7/64 会走**（9000 it 预算下），加上头块才变成 24–51/64
—— 头块不是装饰，是让这一族在现预算下站起来的条件（2 个 seed 都是）。

**事实 2 — flight 惩罚是唯一"三赢"的开关。**（在偏差配方上验证的）
flight 0.2288 → 0.0170/0.0334/0.0426（3/3 seed）；**站立从 62–64 次摔 → 1 次**
（倾角 72° → 3.9°，离地 12–23 mm → 0.51 mm）；漂移 DC 22.9 → 5.6 deg/s。
它**从来没在好的那一族（官方配方+头块）上跑过**。

**事实 3 — 摔倒的定位变了。** 直行（vx=0.2）与转向（±0.6）命令下所有臂都是 **0/64 摔**；
摔只发生在**站立/待机**以及训练分布里的推力上（基线族 `fell_over` 占 env-step 2.9–3.3%，
官方配方族 0.00–0.17%）。所以"走直线会摔"是错的，"站定会摔"才是当前的真问题。

**参照系（重要）**：官方 released 在**它自己的模型+舵机**上 4.5°/20 s（11.1°/m），
通道过原点、左右对称（54.8 % vs 54.2 %），站着不能转（1.1 %/5.2 %）——
即官方没有任何"自然转弯"可以当转向用。我们最好的臂按里程是 33°/m（align_fwd），差 3×。
官方 runner cfg 是 50000 it，我们一直只训 9000 —— **预算差 5.5×**。

## 2. 改进思路（按证据强度排序）

1. **换族**：把 GPU 从"12 偏差配方上继续加开关"转到 **官方配方 + 头块**。
   理由：事实 1。这也是唯一一条同口径下全面更好的路。
2. **加 flight**：在好族上跑 flight 惩罚。理由：事实 2（三赢），且从未在该族上测过。
3. **加预算**：9000 → **12000 it**（2048 env）。理由：官方 50000 it；仓库自己的
   曲线显示直行度**不是训练时长的单调函数**（`ours_head_ck05000` 109° vs 最终 427°），
   所以靠 checkpoint sweep 读每个 run 的最佳点，而不是只看最后一个。
4. **测速度相变**：把命令上限压到 **0.15 m/s**（`MICRODUCK_CMD_LIN_MAX=0.15`，新增开关，
   已被单变量测试锁住）。理由：冻结 ck7000 的速度扫描在 0.10→0.20 m/s 之间测到相变
   （每步冲量 ×93、净转角 2°→114°），而用户自己也提过"是不是速度太快导致的"。
   <0.10 时策略根本不动，所以取 0.15。
5. **不再做**：turn-first（已证伪，gain 1.9–5.7 % vs 官方 57.6 %）、继续加偏差开关、
   `feet_max_width` 单独使用（事实 3 的第三行：它没修好站立，还把离地拉到 86 mm）、
   extension 队列的 yawdc s43/s44 + flight_yawdc（偏差配方，已被本族取代）。

因为原来的 `vx=0.0` 评估在零命令下会返回 `n_envs_insufficient_data = 64` 的空结果）→
步态取证 + 验收表。

## 4. 这次顺手修掉的两个坑（都会静默污染结论）

1. **`run_arm_once.sh` 的 run 目录解析**：重名时 `MICRODUCK_TASK_NAMED_RUNS=1` 会把新 run
   改名成 `<name>_r2`，而脚本先看"约定路径是否存在"→ 导出了**上一次训练**的 checkpoint
   （已用 ONNX 权重比对证明：`max|Δ| = 0.000e+00`）。现在以训练日志为准 + checkpoint 必须
   晚于本臂开始时间。→ 否则 family B 的 7 个臂会重演同样的错。
2. **零命令评估是假阴性**：`len(t) < 20`（0.4 s）就丢环境，而零命令下"摔"正好表现为
   立刻 reset → 全部 64 个环境被丢掉，看起来像"没数据"。现在每个臂都跑真正的站立探针。

## 5. 判定标准（提前写死，避免事后解释）

- **主指标**：`align_fwd` 的 33°/m（走动 med|Δψ| 64.3°）要被打败；
  目标档是官方的量级（11°/m）。
- **站立**：站立探针 `resets ≤ 1`、`tilt_max < 10°`、`clearance < 8 mm`（踏步阈值）。
- **flight**：`< 0.05`（对齐 ck7000 的 0.12 → 官方 0.00 之间）。
- **速度**：净速度 `≥ 0.09 m/s`（= ck7000 档），下滑到 0.03 就说明"变直是靠变慢"。
- **每臂看 checkpoint sweep 的最佳点，不只看最后一个**。
- 结论必须同批次重跑（跨日期评估器漂移 ~10°），且 seed ≥ 3。
