> 当前模型 = `logs/rsl_rl/velocity/Mjlab-Velocity-Flat-MicroDuck/…onnx`，checkpoint `model_11999`）

## 0. 结论（先回答）

**主因在训练策略侧：奖励里没有给"走直"定价，观测里又没有航向反馈 —— 走歪既没被定价，也无法被观测。**
不是舵机数据，也不是模型结构。

需要说清楚的一点（否则容易误导）：**我们的配置文本和官方那套几乎完全相同**
——`git diff -w origin/develop HEAD` 只有 1 行功能性差异（`init_std`），官方同样
`rel_heading_envs = 0.0`。所以差异**不在配置文本本身**，而在于：
在"直线行走不被定价"这个欠约束下，**我们的训练收敛到了一个坏盆地**
（靠左右步态不对称，把步态锁相的偏航振荡整流成净偏航），而官方那次训练收敛到了正常步态。

三段式分解（同一环境，只换一个变量，vx=0.4 m/s、DR 关闭、16 个种子、20 秒）：

| 策略 / 硬件 | **路径效率** ↑ | 中位横向漂移 ↓ | 偏航偏置 |
|---|---|---|---|
| 官方 `alpha_walking` + XL330（官方硬件） | **0.842** | 0.98 m | −1.2 deg/s |
| **我们的配方** + XL330（换舵机**前**） | 0.486 | 3.37 m | −4.8 deg/s |
| 我们的配方 + HD-1910（**当前**） | 0.362 | 3.08 m | −6.2 deg/s |

> 路径效率 = 沿"起步朝向"前进的距离 ÷ 实际走过的总路径长度。**1.0 = 一条直线，0 = 原地转圈。**

- **0.842 → 0.486**（同硬件、同环境、只换策略）是最大的一段 ⇒ 策略侧的问题。
  证据：`walk.onnx` 是**换 HD-1910 之前**、在 XL330 官方硬件上、4096 环境训出的走路策略，
  它在 XL330 环境里**照样走歪**（偏航偏置 −4.6±1.8 deg/s，20 秒净转 −92±36°，横向漂 1.54 m）。
- **0.486 → 0.362** 这一段是 HD-1910 的贡献 ⇒ 舵机/模型是**次要放大因素**
  （HD-1910 的 kp_fw=32 比 XL330 的 200 软 6 倍，同样会放大已有的不对称）。

>
> 上面那行"模型几何几乎没有贡献"来自一个 **8 环境 + 旧策略** 的噪声较大的测量。

### 0.1 受控单变量实验：只改质量，走歪从"几乎没有"变成"严重"

两个模型 XML 的差异**只有 24 行 `<inertial>`**，其余（body / joint / geom / 限位 / 轴 /
执行器 / 默认值）**逐字节相同**；总质量 737.24 g vs 779.24 g（+42 g = 14×3 g）。

同一个策略（新 run @~4300 迭代）、同一套执行器参数、同样 16 环境 × 20 秒、vx=0.2：

| 只改质量 | 路径效率 | 偏航率偏置 | 20 秒净偏航 | 直线度 RMS |
|---|---|---|---|---|
| **737.24 g**（XL330 模型） | **0.751** | **−0.04 deg/s** | **−1.5 ± 89.5°** | 0.180 m |
| **779.24 g**（HD-1910 模型） | **0.501** | **−5.48 deg/s** | **−110.2 ± 87.5°** | 0.279 m |

**+42 g（+5.7%）的质量，把偏航偏置从"基本为零"推到 −5.5 deg/s，净偏航从 −1.5° 推到 −110°。**
（均值差 108°，标准差 ~88，n=16 ⇒ 约 5σ，不是噪声。）

**怎么解读（重要，别读成"重量是根因"）**：
- 这个策略**就是在这台 779 g 的机器上训练的**，它在自己的训练点上走歪，
  而在一个**轻 5.7% 的（分布外）**机器上反而走直了。
- 说明这个策略在航向上处在**临界稳定**状态：质量稍微一动就翻到另一个行为模式。
- 而它之所以会落到这种临界点，**是因为奖励里从来没有给"航向"定价**（§3.1）——
  没有任何梯度把策略推离这个脆弱的工作点。
- 所以正确的说法是：**策略（欠定价）是因，重量/舵机是扣动扳机的那一下。二者不是二选一，而是耦合的。**

这同时解释了另一件事：为什么换舵机之后的几次 run **种子间方差极大**
（同一命令下有的种子走直、有的种子转一整圈）—— 临界稳定系统的典型特征。

**"头一直乱晃"不是走歪的原因**（见 §4）：把头颈四个关节动作全部冻结后，走歪**没有改善，反而略差**；
而且实测走歪的整流源是**腿、不是头**。

置信度：策略欠定价为**因**是**高**；质量敏感性为**触发器**是**高**（单变量、5σ）；
但"若在 737 g 上训练就能得到直走的策略"**未验证**（需要重训，属推断）。

## 1. 我们现在到底观察到什么（先纠正一个前提）

用户描述是"起步直、越走越偏"。实测**比这严重得多**：不是轻微跑偏，而是**在绕圈**。

当前策略 `model_11999`，直行命令 (vx=0.2, vy=0, wz=0)，16 环境、20 秒、DR 关闭：

| 指标 | 值 |
|---|---|
| 偏航率偏置 | −5.1 ± 9.7 deg/s |
| 20 秒净偏航 | **−103 ± 193°**（部分种子转了 300°+） |
| 沿目标方向前进 | 1.19 m |
| 实际走过路径长 | **4.8 m** → 路径效率 **0.249** |
| 航向保持在 ±30° 以内的环境比例 | 6% |

即：它走的 4.8 m 里有 3.6 m 花在转弯上。这正是"起步直、越走越偏"的成因——
一个未被抑制的恒定偏航角速度，在无航向反馈的情况下积分成越来越大的航向误差。

**关键事实：观测里既没有航向、也没有机体线速度。**
观测合同（ONNX metadata 实测）只有：
`base_ang_vel(3), projected_gravity(3), joint_pos(14), joint_vel(14), actions(14), twist(3), head_pose(4), body_pose(6)`。
`base_lin_vel` 已被从 actor 观测里删除（critic 专用），且 `USE_PROJECTED_GRAVITY=True` 连线加速度也没有。
——策略能"看见"偏航**角速度**，但**看不见**自己已经偏了多少、也看不见横向位置。
所以一旦它没能把偏航角速度压到 0，误差就会无界累积，**没有任何闭环路径可以纠正**。

## 3. 归因：为什么是"欠定价 + 不可观测"

### 3.1 没有任何一项奖励是"偏航角"的函数

- 唯一与偏航有关的项是 `track_angular_velocity`（权重 +2.0，std²=0.5）。
  它的实现只对**角速度误差**计费（`z_error=(cmd_wz−ω_z)²` 再加 xy 角速度误差），
  **没有任何一项是偏航角本身的函数**。
  （注意：mjlab 里这个函数的 docstring 声称支持 heading 模式，但实现里并没有。）
- **它只占收益的 2.1%**：iter 11999 时实测 `+0.0714`，单步净收益 `+3.367`；
  其 raw 值 0.0357/1.0 意味着合成角速度误差已达 **1.291 rad/s**，早已深入高斯尾部。
- **漂移的边际价格**（由该 raw 值闭式推出）：偏航率偏置 0.02/0.05/0.10/0.50 rad/s
  分别只值 **0.0017% / 0.011% / 0.042% / 1.06%** 的收益。
  也就是说：**0.1 rad/s 的偏航率偏置 = 20 秒偏航 115°，代价只有 0.0014/步。**
- `angular_momentum` 权重 −0.02，实测 raw **−8.9e-7 ≈ 完全死的**；
  `body_ang_vel` 只管躯干且**按构造排除了 z 分量**。

我另做的奖励项实测（当前模型、直行命令、16 环境、12 秒）：

| 奖励项 | 实测 / 上限 |
|---|---|
| `track_linear_velocity` | **+1.626 / 2.0**（线速度跟踪良好） |
| `track_angular_velocity` | **+0.406 / 2.0**（航向基本没在管） |
| `upright` | +1.885 / 2.0 |
| `head_pose_tracking` | +1.977 / 2.0 |
| 单步总奖励 | **+7.55**，航向项只占 **5.4%** |

一句话：**它把"走多快"学得很好，把"走多直"基本放弃了。**

### 3.2 机制：步态锁相的偏航振荡被整流成净偏航（Agent G 实测）

在 16 环境的直行数据里，两个半步的偏航率是 **+10.6 vs −18.3 deg/s**
（半步不对称 **+28.9 ± 11.7 deg/s**），而整个 20 秒的直流偏置只有 −4 deg/s
——**AC/DC = 16.7×**。

也就是说：**漂移是约 6% 的整流残差**，来自一个步频锁相的 ±66 deg/s 偏航振荡。
这正是"速率高斯"看不见的工况：一个 std=0.707 的高斯在 66 deg/s（1.15 rad/s）处
已经几乎没有梯度，而整流出来的那 4 deg/s 直流分量更不可能把梯度做出来。

**而且这个整流源是腿，不是头**：同一批数据里头部半步不对称 ≤0.6°、头部标准差只有 1.8–2.3°。

### 3.3 左右不对称：症状，不是根因

左右腿关节角均值对比（16 环境 × 20 秒）：

| 关节 | 我方（左 / 右） | 官方（左 / 右） |
|---|---|---|
| hip_yaw | −2.34° / +1.96° | −4.07° / +4.18° |
| **knee** | **−7.90° / −1.10°** | +4.19° / −4.48° |
| **ankle** | **+16.98° / −23.54°** | +21.46° / −22.23° |
| hip_roll | +0.98° / −0.77° | −4.64° / +4.69° |

官方左右几乎完美镜像（差异 < 1°）；我方膝盖差 **6.8°**、脚踝差 **6.6°**。

**注意因果方向**：正在转弯的策略当然会表现出不对称腿型，所以这张表**说明机制**，
但**不是**"不对称是根因"的独立证据。真正的证据是 §0 的三段式分解和 §4 的消融。

### 3.4 训练预算：不是问题（更正）

当前 run：12000 迭代 × 2048 环境 × 24 步 = **5.9e8** 环境步。
AGENTS.md 的指引是 4000–6000 迭代 @ 4096 环境 = **3.9e8 – 5.9e8** 步。
**当前 run 正好落在指引上限**，所以预算**不是**问题（我先前把这里算错了 10 倍，已更正）。

这也符合 Agent G 的旁证：stance 相关税收的 raw 值从 iter 750 起就**一直平稳**，
说明策略早已收敛——**这是缺一项，不是没练够**。

### 3.5 关于命令分布（更正）

先前我判断"部署时的精确直行工况是零测度、训练里几乎不出现"——**这是错的**。
`rel_forward_envs = 0.2` 是从上游继承下来的、没有被覆盖，它给出了一个
**精确的 (vy=0, wz=0, vx∈[0.3,0.4]) 桶，约占总经验的 12.8%（早期约 17%）**。
所以直行工况**确实被采样了**。
真正零测度的是 `head_pose` / `body_pose` 的精确零命令（`zero_command_prob=0.0`），
而部署时恰恰发的是零。

## 4. 专门验证："头乱晃导致走歪" —— 不成立

用户的假设值得单独、直接检验。

**为什么它听起来合理**：头部组件 **289 g ≈ 整机 37% 质量**；
`angular_momentum_penalty` 权重只有 **−0.02**（实测≈0）、`body_ang_vel` 只有 **−0.05**
（且按构造排除了 z 分量）；而 `head_pose_tracking` 权重 **2.0**，是**收益第一大正项（43.6%）**；
课程把 `head_yaw` 命令范围一路放宽到 **±1.40 rad**；
`per_joint_posture` 的选择器 `^(?!passive_|.*neck.*|.*head.*).*` **把头颈整个排除在姿态奖励之外**
——即：头部摆动在奖励里几乎不受约束，甚至被付费（把头保持在 HOME 只能拿到 0.5015/1.0，
等于有 **0.997/步 ≈ 29.6% 的收益可以靠甩一个 289 g 的头白拿**）。

**直接消融实验**（把 neck_pitch / head_pitch / head_yaw / head_roll 四个关节的**动作清零**），
16 环境、20 秒：

| 配置 | 净偏航 | 路径效率 |
|---|---|---|
| 基线 | −65 ± 180° | 0.412 |
| **头颈完全冻结** | **−79 ± 249°** | **0.257** |
| 只冻结 head_yaw | −191 ± 211° | 0.318 |
| 只冻结 neck_pitch + head_pitch | −88 ± 219° | 0.242 |

**结论：把头彻底冻住，走歪一点没好转，反而更差。**
加上 §3.2 的实测（整流源是腿不是头），**头晃是共症状，不是原因。改头部奖励不会修好走歪。**

**方法学保留**（Agent G 指出，我接受）：
- `--ablate-head` 是把头部**动作清零**（让头变成被动），**不是**把头刚性锁在 HOME，
  所以"冻结"应理解为"取消主动头控"。
- `--freeze-pose-cmd` 在评测里几乎是空操作：eval 只有约 22 秒，
  而 `head_pose` 课程要到 12000 步（=240 秒）才进第 2 档，两臂看到的都还是 ±3° 的头部命令。
- 16 环境的偏航偏置离散度 ±13.7 deg/s（SE≈3.4），两次 8 环境基线本身就差 5.3 deg/s，
  所以"−0.7 → −14.6 deg/s"这个差异约 2σ，**不宜当作强证据**；§4 的结论主要靠 16 环境那组。

**一个仍然成立的旁证**（Agent G 的 ONNX 梯度探针）：策略对**头部状态**的敏感度
（∂leg/∂neck_pitch ≈ **0.75**，左右踝反号）远高于对**偏航命令**的敏感度（∂leg/∂twist_wz = 0.052），
相差 **15–20 倍**，且头→腿是**反对称**的。
所以"真机上的头部抖动会灌进步态"这条链是存在的——**它只是不是仿真里走歪的原因**。
（Agent G 另标记：运行时对策略施加 `action_scale 0.9` 以及训练里没有的头/腿低通滤波，
这是"仅真机出现的头晃"的一个活跃嫌疑。**已核实属实**：`robotd/src/control.rs:76`
确为 `action_scale: 0.9`，而训练侧 `actions.joint_pos.scale = 1.0`、ONNX metadata 也是 1.0；
`control.rs:15` 也确认存在 "optional first-order low-pass on head and legs"。
这是真实的 sim2real 失配 —— 但官方策略同样跑在 0.9 下且走得很直，
所以它**解释不了"为什么我们歪官方不歪"**，只能解释真机上额外的头部动态差异。）

### 4.1 那"看起来头在乱扭"到底是什么？—— 躯干在甩，头被动跟随

用户观察到的"头一直乱晃"**不是脖子在自己扭**。实测（同一 vx，16 环境 × 20 秒）：

| 指标 | 当前 model_11999 | 官方 alpha_walking | 倍数 |
|---|---|---|---|
| **颈/头关节**自身 std | neck 2.00° / head_pitch 1.60° / head_yaw 1.50° / head_roll 0.60° | neck 1.91° / head_pitch 1.83° / **head_yaw 2.83°** / **head_roll 1.70°** | **基本一样，官方甚至更大** |
| **躯干偏航振荡** std | **11.62°** | **3.14°** | **3.7×** |
| **躯干偏航率** std | **66.4°/s** | **14.9°/s** | **4.5×** |

头是**刚性连在躯干上**的（经过颈部）。躯干每步左右甩 ±11.6°，头就跟着甩 ±11.6° ——
**在 viewer 里看到的就是"头在乱扭"**，但驱动它的是躯干，而躯干是被腿甩起来的。

**因果链（每段都有实测相关系数，n=16）**：

```
左右腿步态不对称  ──r = −0.82──▶  净偏航（走歪）
                  ──r = −0.68──▶  躯干偏航率振荡 ──▶ 头作为刚体跟着甩（"头乱扭"）
```

也就是说：**"头乱扭"和"走歪"是同一个根因的两个可见面**，不是两个独立问题。
修好偏航（§6 已启动的训练）应当**同时**改善这两者。

这一点还让 §6 的修复更有把握：官方实测躯干偏航振荡只有 3.14°，
说明 **±11.6° 是"可逃脱的"、不是这种步态的固有代价** —— 所以给偏航角定价是正当的，
不属于 AGENTS.md 警告的"给逃不掉的部分收税"。

**R4 —— 把"直行桶"显式化**

## 6. 最终选定的改法（2026-09-14）

### 6.0 决策：只改一处核心 —— 给 `heading_hold` 加"双门控"

面对"舵机数据 / 模型结构 / 训练策略"三条线索，本文的结论是**训练策略**（§0–§3、§4）。
修复手段有三个候选，最终**只选一个**：

| 候选 | 决定 | 理由 |
|---|---|---|
| **`heading_hold`（偏航角项）** | ✅ **采用** | 唯一直接给"偏航角"定价的项（§3.1：全栈原本一项都没有）；**目标导向** —— 策略可自由选择"把步态改对称"或"反向补偿"，不必规定它怎么做 |
| `gait_symmetry`（摆动时间对称） | ⛔ 默认关闭（代码留好） | ① 是**代理指标**（摆动时间不平衡 ≠ 净偏航力矩）；② **会误伤命令转弯** —— 转弯本来就要求不对称迈步，而本项在走路环境无门控（rollers 没这问题，因为它 heading 命令是关的；走路环境 \|wz\| 到 1.0 还有 15% 原地旋转桶）；③ 一次只改一件事，失败时也分得清责任 |
| `rel_heading_envs: 0.0 → 0.3` | ⛔ 不做 | 它要靠"偏航率内环"才能闭环，而这个内环当前是坏的（`track_angular_velocity` 实测只有 0.406/2.0）。**官方也是 0.0** 却走得很直 ⇒ 不是必需的，属于引入新目标 |

**原则：只动奖励，不碰 61 维观测合同 ⇒ 运行时不需要改，策略仍可与官方策略热插拔。**

| 2 | 走路环境接入 `heading_hold`（权重 0 → +1.5，4 级台阶 iter 300/611/949/1300） | `microduck_velocity_env_cfg.py` |

本次只是把它接进走路环境，并补上两道门。

### 6.2 两道门（最容易做错的地方）

**（一）偏航命令门** —— 走路环境**本来就会命令转弯**（`ang_vel_z ∈ (−1,1)` 均匀 +
15% 原地旋转桶），无脑奖励"保持出生航向"等于付钱让策略抗命。

- `|cmd_wz| > 阈值`(0.2) 时：**参考航向持续刷新为当前航向**，该项返回 **0**；
- `|cmd_wz| ≤ 阈值` 时：冻结参考并计算高斯。

这样**不需要边沿检测** —— 转弯结束前的最后一次刷新，天然就是"直线段起点"的航向。

**（二）速度门 —— 这是我第一版实现里的真实缺陷，必须修**

第一版没有速度门，于是**站在原地的策略能白拿满额奖励**（站定天然完美保持航向）。
按实测数字推演，这会让"站定"得分**超过**"歪着走"：

```
站定   ≈ track_linear 1.34 + heading_hold 1.5  = 2.84
歪着走 ≈ track_linear 1.63 + heading_hold ~0.2 = 1.83
```

也就是说，这一项会给"还不会走直线的策略"挖出一个**"停下就赢"的局部最优** ——
正是 AGENTS.md 明令禁止的形态（正奖励不许落在可刷分的状态上）。

修法沿用**仓库自己的先例**：`feet_air_time_progress_gated` 就是用 `vel_gate_ref`
防"原地踏步刷分"（原文："otherwise a fast in-place flutter farmed this"）。
门是**乘性**的：

```
gate = clamp(|root_link_lin_vel_b[:, :2]| / 0.15, 0, 1)
reward = hold × gate   (再加偏航命令门)
```

- 静止 → 0（没得刷）；达到参考速度 0.15 m/s → 满额
- **当前策略实测 vx ≈ 0.207 > 0.15 ⇒ 门全开**，不会削弱它现在能拿到的梯度
- 乘性而非再加一个速度奖励 ⇒ 不与 `track_linear_velocity` 重复计费
- 不设 floor（与 air_time 的 `gate_floor=0.25` 不同）：权重本身是爬坡进来的，
  不存在"技能摸索期被饿死"的问题
- `vel_gate_ref=0.0` 时完全关闭 ⇒ rollers 的调用点逐字节不变

**（三）门控关闭返回 0 而不是 1**：两者对梯度的作用**完全相同**（都是常数），
但常数 1.0 会在约 80% 的步数上给正奖励栈注入 ~1.2/步的**无梯度**奖励，
稀释其他所有项的相对影响（AGENTS.md："比较奖励质量而不是权重"）。
仓库既有惯例（`stillness_at_zero_command`、`no_stepping_penalty`、
`feet_air_time` 的命令门）也都是返回 0。

### 6.3 量级标定（为什么是 1.5）

训练日志里单步净收益约 **+3.37**，本项满分 +1.5：

| 航向误差 | 本项损失 | 占净收益 |
|---|---|---|
| 17°（0.3 rad） | 0.43/步 | ≈13% |
| 57°（1.0 rad） | 1.50/步 | ≈44% |

对照现状：同样 1 rad 的航向误差在 `track_angular_velocity` 下只值 **0.04%** —— 相差约 **350 倍**。

课程用 **4 级台阶**而不是 2 级：`reward_weight` 是阶跃函数（不是插值），
2 级会在 iter 300 处产生 0 → 0.75 的悬崖。AGENTS.md 记录过
"wandb 指标正好在课程边界处下台阶 = 课程节奏错了"。

## 7. ⚠️ run 目录名 ≠ 策略版本（一个很容易踩的坑）

`logs/rsl_rl/velocity/` 下有**两套命名约定**，它们不代表新旧或配置差异：

| 命名形式 | 何时出现 |
|---|---|
| `2026-09-14_13-09-24_velocity` | **默认**：mjlab 原生命名 `{时间戳}_{run_name}` |
| `Mjlab-Velocity-Flat-MicroDuck`（固定名） | 设了 `MICRODUCK_TASK_NAMED_RUNS=1` 时 —— 供**训练队列**脚本轮询用（见 `train_cli.py:63-115`） |

所以 `Mjlab-Velocity-Flat-MicroDuck/` 只是"被队列起的那次 run"，
**不是"当前配置"的同义词**。该目录里的 `model_11999` 训练于
**09-11 20:36 → 09-12 00:18**，而 `heading_hold` 是 **09-14** 才加的
（决定性证据：该 run 的 `params/env.yaml` 里 `heading_hold` 出现 **0 次**，
而新 run 的 `params/env.yaml` 出现 4 次；奖励项 21 vs 22 项）。

**判断某次 run 用了什么策略，只能看它自己的 `params/env.yaml`，不能看目录名。**

另外注意：新版 `train_cli` 会**随训练进度反复覆盖**同名 ONNX
（每 250 迭代一次，约 4 分钟），所以在 viewer 里打开的"新 run 的 ONNX"
是**训练中的快照**，与一个已经跑完 12000 迭代的策略**不可直接对比**。

## 8. 边界、未决项与诚实的保留

1. **官方策略的对照速度不匹配**：官方在 vx=0.2 下只走到 0.037–0.08 m/s（严重欠跟踪），
   此时它的"直"是低速下的直。因此**所有关键对比都在 vx=0.4 重做过**
   （官方实测 0.186 m/s、我方 0.331 m/s）。§0 表格用的是这一组；
   路径效率是尺度无关量，用它比较才成立。
2. **官方训练配方不可得**：`alpha_walking.onnx` 来自 `apirrone/microduck_runtime`。
   我们能确认配置文本与官方几乎相同、观测合同一致，但**无法**知道官方那次 run 的种子、
   初始化、迭代数和是否走了 rough 地形（该 run 的角色名是 `BEST_alpha_walking_rough`）。
   所以"官方更直"是**事实**，"为什么它进了好盆地"属于**推断**。
3. **play 模式奖励汇报陷阱**：课程是**按步数**的，评测时从 step 0 重开，
   于是 `stance_hip_yaw` / `action_over_limit` / `neck_motion` / `no_stepping` /
   `stillness_zero_cmd` / `head_pose_bias` 全部是权重 0，`action_rate` 是 −0.1 而不是 −1.0。
   这解释了为什么我实测的单步总收益是 +7.55、而训练日志是 +3.367。
   它**不会改变**一个冻结 ONNX 的行为（奖励 ≠ 策略），所以**不是病因**，
   但任何 play 模式的奖励审计都必须声明这一点。
4. **执行器维度无法完全隔离**：我们的策略在 XL330 参数下会直接摔倒
   （kp_fw 32→200 是 6 倍刚度跳变），所以"同一策略分别在两种执行器下评测"这条最干净的路走不通。
   §0 的硬件段（0.486→0.362）是"同一配方在两种硬件下各自训练的产物"，**不是**纯粹的参数隔离。
5. **HLS2909 那一格没跑通（未纳入结论）**：`hls2909_walk.onnx` 在其原生环境里几乎不动
   （沿目标方向前进 −0.06 m、vx −0.005 m/s、3/16 摔倒）。
   我先用错了模型版本（见 §2.3 的 provenance 陷阱），**修正为正确的 800.24 g 模型后结果不变**，
   所以原因不是模型版本，而是该 checkpoint 本身在这套评测配置下不走路
   （大概率是没复刻该 run 的 `stiff_frictionloss: true` 等设置）。
   因此"我们配方在 HLS2909 一代是否也走歪"**没有结论**——但 XL330 与 HD-1910 两代已经足够支撑 §0。
6. **一个已发现的次要隐患**（Agent E）：`train_velocity_hd1910.log:52` 显示
   09-10 那次走路训练用的是**被后续覆盖的旧参数批**（kt=0.7358、m5_alt 摩擦），
   18:51 参数被重写。这是均匀增益误差，**不产生左右偏置**，但会让策略学到的动力学与部署略有出入。
7. **文档漂移**（Agent E）：文档里声称磁盘上 `m5.json` 的 `kd=192.68`，
   实际提交的 `m5.json:17` 是 `kd=0.346`。相关文档需要更正。
