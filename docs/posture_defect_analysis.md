## 0. 一句话结论

**两个缺陷都是策略问题,不是硬件问题,也不是官方配方的问题。**

| 缺陷 | 判定 | 决定性证据 |
|---|---|---|
| **岔腿 / 姿势怪** | **策略(奖励没定价)** | 官方策略在同一套官方配方下:外张 **+0.37°**、脚间距 −0.68 mm、**完全正常**;本地策略:+5.78° 外张、脚间距 −13.3 mm、`hip_yaw` 被顶到硬限位 |
| **头歪** | **策略(奖励没定价)** | 官方颈部摆动 **0.75°**;本地 **16.4°**(步频 2.15 Hz)。把头/颈动作钳到 HOME → 头摆从 22.5° 掉到 **2.5°**,而机器人**照样走**(0.172/0.200 m/s,0 摔)⇒ 完全是可逃的 |
| **不是硬件** | 已排除 | ① 官方策略失败**不是**因为 HD-1910 舵机弱;② 本地缺陷在舵机刚度提高 6 倍(`kp_fw` 32→200)后**原封不动** |
| **不是官方配方** | 已排除 | `git diff -w origin/develop HEAD -- src/mjlab_microduck/tasks/` 的**功能差异只有一行**(`init_std 1.0→0.5`),其余全是注释 |

**真正的根因是一个正反馈陷阱**(见 §3):策略早期学了**深蹲步态** → 姿态奖励饱和到死 →
`hip_yaw` / 颈部失去一切约束 → 摆出歪姿势 → 深蹲进一步被固定。

## 2. 为什么奖励没管住 —— 定价缺失的量化

### 2.1 实测的每项奖励(忠实环境重放当前 ONNX,cmd vx=0.2,12 s)

| 奖励项 | 权重 | 每秒贡献 | 占总奖励 |
|---|---|---|---|
| air_time | 3.0 | +2.07 | 27% |
| upright | 2.0 | +1.90 | 25% |
| head_pose_tracking | 2.0 | +1.83 | 24% |
| track_linear_velocity | 2.0 | +1.52 | 20% |
| track_angular_velocity | 2.0 | +0.42 | 5.6% |
| dof_pos_limits | −1.0 | −0.058 | — |
| body_ang_vel | −0.05 | −0.045 | — |
| **pose** | **1.0** | **+0.026** | **0.34%** ← 几乎是死的 |
| action_rate_l2 | −0.1 | −0.014 | — |
| angular_momentum | −0.02 | **−0.000003** | 完全无效 |

**总奖励 ≈ 7.6/步。**

### 2.2 两个缺陷的代价(独立算法,数字互相印证)

| 缺陷 | 每步代价 | 占总奖励 | 出处 |
|---|---|---|---|
| 颈部 ±15.7° 摆动 | 0.093–0.12 | **1.1–1.7%** | Agent A(Bessel 恒等式 `exp(−z)I₀(z)`,z=0.137) |
| 16° 外八字(hip_yaw) | 0.0042 | **0.077%** | Agent A;我实测 pose 项 0.026/7.6 = 0.34% |
| **两者合计** | ~0.13 | **< 2%** | |

**结论:两个缺陷合计只花掉约 1–2% 的奖励,而策略从"用头当配重"里赚到约 0.3–0.5/步。**
这是一笔**理性的交易**,不是训练失误。

### 2.3 `pose` 项为什么是死的(结构性问题)

mjlab 的 `variable_posture`(`.venv/.../mjlab/tasks/velocity/mdp/rewards.py:385-466`)是:

```python
return torch.exp(-torch.mean(error_squared / (std**2), dim=1))
#            ↑ 注意:先对 10 个腿关节取平均,再取 exp
```

走路时脚踝**必须**大幅摆动(+45°/+48°)。以 std=0.25 计,脚踝一项就是
`(0.79/0.25)² = 9.99`,10 个关节平均后 ≥ 3.6 → `exp(−3.6) = 0.027`。
**一个关节把整项按到地上,顺带把 `hip_yaw` 的梯度也一起埋了。**
`hip_yaw` 偏 16° 摊到 10 个关节里只值 0.0087。

官方策略没掉进这个陷阱(它腿贴着 HOME,pose = 0.946),所以我们遇到的
**不是"配方错",而是一个陷阱:一旦掉进去就出不来**。

## 3. 头歪的机理:拿 289 g 的头当配重

### 3.1 是策略主动摆的,不是舵机拉不动

原始动作取证(**这是决定性的**):在忠实环境里逐帧记录策略的**指令目标**
(`target = default_joint_pos + action`,`scale=1.0`,`use_default_offset=True`):

- `neck_pitch` **指令本身**是 ±15.7° 的正弦,频率 2.15 Hz(**正好等于步频**)
- 关节以 **66°(86 ms)** 相位滞后跟随,振幅 16.77° —— 跟随得很好
- 其他所有关节在步频处也有 34–66° 的滞后(44–86 ms),这是执行器带宽特性

所以:**不是重力下垂,不是扭矩不够,是策略在主动甩头。**

**消融实验**(把颈部动作冻结为 0 = 命令回 HOME):

| | 基线 | 颈部冻结 |
|---|---|---|
| 头相对躯干 nod std / p2p | 21.4 / 68.9° | **2.3 / 6.8°** |
| 头世界系 pitch std | 11.5° | **6.1°** |
| 颈部占空比饱和 | 64.5% | **0%** |
| 颈部平均 |扭矩| | 0.753 N·m | **0.154 N·m** |
| **行走速度(0.20 目标)** | — | **0.172 m/s,0 摔** |
| **躯干倾角 mean** | **2.6°** | **5.9°(max 14.9°)** |

**两件事同时成立**:
1. 头摆完全可以消除,而且**不影响行走能力**(0 摔,速度 86%);
2. 但**躯干会晃 2.7 倍** —— 所以策略是**在拿头当平衡配重**(289 g,占整机 37%)。

### 3.2 硬件能不能做到?能,而且余量很大

Agent D 的净空计算(MJCF + 已安装参数):

| | 值 |
|---|---|
| 头部组件质量 / 占比 | 288.93 g / **37.08%** |
| `neck_pitch` 轴力臂 | 75.58 mm |
| 静态保持扭矩 @HOME | **0.0182 N·m** |
| 含躯干加速度的峰值 | **0.0314 N·m** |
| 舵机堵转 | **0.9227 N·m** |
| **余量** | **29×** |
| 有效刚度 K | 4.813 N·m/rad |
| 固有频率 / 带宽 | 5.32 Hz / **6.64 Hz** |
| **2.17 Hz 扰动能把头推动多少** | **0.42°** |

**舵机完全能稳住头。** 而策略命令的 ±21°/2.17 Hz 摆动需要占空比 **1.03(>100%)**
→ 64.5% 的时间在饱和。**策略要求了一个它给不出的动作,而不是给出它本来能给的"静止"。**

### 3.3 为什么它要甩头

头部 289 g、75.6 mm 力臂,±16° 摆动 ⇒ 头质心水平行程 ±21 mm @2.15 Hz
⇒ 加速度 ~3.8 m/s² ⇒ 反作用力 ~1.1 N(约体重的 14%)。这给了策略可观的
姿态控制权限 —— 消融里"冻结后躯干晃 2.7 倍"就是它的价格标签。

## 4. 岔腿的机理:`hip_yaw` 被顶死在机械限位上

### 4.1 实测

| | 走路 (vx=0.2) | 站立 (vx=0) |
|---|---|---|
| `left_hip_yaw` 平均 | **+15.97°** | **+30.44°** |
| `right_hip_yaw` 平均 | **+16.50°** | **+25.45°** |
| 距硬限位 1° 内的步数占比 | **48.1% / 46.8%** | **100% / 100%** |
| `hip_yaw` 原始动作 mean\|a\| | 1.33(max 10.01) | **10.14(max 10.27)** |
| 台阶限位的步数占比 | 40.7%(Agent D) | — |
| 占空比饱和 | **87.5%**(Agent D) | — |
| 平均 |扭矩| | **0.858 N·m = 93% 堵转**(Agent D) | — |

**原始网络输出 10.14 rad** —— 而 `scale=1.0`,意味着真机运行时会收到
"HOME + 10 rad" 的位置指令(远超 ±30° 限位)。**这是一个真实的部署隐患。**

### 4.2 是"外八字"还是"整体扭转"?

CPU MuJoCo 正运动学:`left_hip_yaw` 与 `right_hip_yaw` 的轴**在世界系里都是 (0,0,−1)**
⇒ 两只脚上的 +16° 是**同向**的,不是镜像 ⇒ 不是"外八字",而是**整个下半身相对躯干
扭转了约 28°**。绕垂直轴的重力矩**恰好 0.000 N·m**(Agent A/D 都算了),
所以这**不可能是重力下垂,只能是策略有意为之**。

站立时:躯干 91 mm(标称 120 mm),脚间距 31 mm,前后劈叉 117 mm,双脚同向扭 28°。

### 4.3 为什么会这样:支撑多边形

Agent D 的全脚掌支撑多边形计算(复现了仓库里 54.7 mm 的旧数字):

| 站姿 | 支撑多边形 | 横向余量 | **前后余量** |
|---|---|---|---|
| HOME | 124.84 × 54.00 mm | 62.39 mm | **20.41 mm** |
| +16° 双脚同向扭 | 133.28 × 73.71 mm | +8.44 mm(+6.8%) | **30.60 mm(+36.5%)** |
| +5° 外张 | 140.70 mm 横向 | +16.3% | — |

**这台机器人最脆弱的轴是前后(20.4 mm vs 横向 62.4 mm)—— 正是文档记录的前扑摔倒模式。**
`hip_yaw` 绕垂直轴转脚,**零扭矩代价**换 +36.5% 的前后支撑余量。
**所以"扭转站姿"本身是个好交易**;坏的是**叠在上面的 ±28° 摆动**
(87.5% 占空比饱和、93% 堵转)。

## 6. 代码改动(已实现并验证)

### 6.1 新增 MDP 函数(`src/mjlab_microduck/tasks/mdp.py`)

1. **`neck_joint_vel_deadband_l2`** —— 带死区的颈/头关节速度惩罚。
   `Σ relu(|v| − 2.0)²`,慢了不罚(执行 `head_pose` 命令需要的慢速摆头免费),
   步频级泵动收费。**只惩罚可逃脱的部分**(与 `head_pose_bias` 只罚 DC 同一个原则)。

2. **`staged_reward_weight_ramp`** —— 多奖励权重线性爬坡课程。
   原 `reward_weight` 是阶跃函数;这是真正的插值,且返回标量
   (`CurriculumManager` 会 `.item()`)。

3. **`per_joint_posture`** —— **结构性修复**。把 `exp(−mean_j(err²/std²))`
   换成 `mean_j(exp(−err²/std²))`。**std 和权重完全不变,只换 reducer**:
   在实测站姿下信号从 **0.015 → 0.47(约 17×)**,而最优解不变。

4. **`joint_deviation_l1`** 增加 `deadband` 参数(向后兼容,默认 0.0)。

### 6.2 速度环境接线(`microduck_velocity_env_cfg.py`)

| 项 | 值 | 触发条件 | 实测代价 |
|---|---|---|---|
| `stance_hip_yaw` | `joint_deviation_l1(hip_yaw)`,w=**−0.8**,deadband=0.10 rad | 走路/站立 | **−0.365/s = 5.6%** 总奖励 |
| `action_over_limit` | `action_over_limit_penalty`,w=**−1.0**,overshoot=0.3 | | −0.076/s = 1.2%(随 rollout 变化 0.03~0.5) |
| `neck_motion` | `neck_joint_vel_deadband_l2`,w=**−0.08**,deadband=2.0 | | **−0.668/s = 10.2%** 总奖励 |
| `pose` | **换成 `per_joint_posture`**(权重/std 不变) | | raw **0.026 → 0.323**(12×) |
| `std_standing/walking["hip_roll"]` | 0.05 → **0.12** | | 目标从"做不到"改成"做得到" |

全部经 `stance_tax_weight` 课程在 **300 迭代内从 0 线性爬坡**
(AGENTS.md:技能还在摸索时上税会让"什么都不做"成为最优解)。

**改动后的实测奖励构成**(同一策略、同一条件,`--no-curricula --hygiene-on`):

| upright | +1.785 | 27.3% | +1.902 |

也就是说:姿态/执行器卫生从**占奖励 0.4%** 提到**约 13%**,

## 8. 三个需要你知道的旁支发现

1. **整机都在舵机的扭矩天花板上**(Agent D):10 个腿关节平均 |扭矩| 0.345–0.858 N·m
   = **37–93% 堵转**。HD-1910 在 5 V 供电下对这台 779 g 的机器人是**偏紧的**。
   深蹲步态会进一步吃掉这个余量 —— 这是"走回来站高一点"的额外理由。

2. **偏航不直是没人定价的**(Agent A):`Metrics/twist/error_vel_yaw = 2.57 rad/s`,
   实测 wz=0 时 20 s 内偏航漂移 +26.7°(某些配置下 194°)。
   原因是 `rel_heading_envs = 0.0` —— **没有任何一项奖励为"朝哪个方向"付费**。
   Agent A 的 R1(对 `wrap_to_pi(yaw)` 做 L1,w=0.5,0.3 rad 死区)能把漂移代价
   从 0.070 提到 0.65/步。**这次没做**,因为用户的两个抱怨里不含这一条;
   但如果重训后机器人还是"边走边转圈",这是下一个要接的项。

3. **官方模型是可以跑起来的**(Agent B 推翻了 2026-09-10 的旧结论):
   之前判断"它连站都站不住"是因为只换了 BAM 参数 JSON,**漏了 `kp_fw`**
   (`bam/mjlab.py:217` 让 `cfg.kp_fw` 覆盖 JSON)。正确的换舵机前配置下,
   官方策略站立倾角 1.56°、走路 3.35°、0 摔。
   **但这不改变结论**:换 HD-1910 参数后官方策略彻底失效(24 摔),
   所以重训是必须的 —— 而且必须用**修好的奖励**重训。

### 已知的测量陷阱(写给后来人)

- **头体在 HOME 处的欧拉角是奇异的**(`jaw_soft` 的名义四元数是纯 −90° pitch),
  直接对它做 roll/pitch/yaw 分解会得到 ±180° 的回绕垃圾。
  正确做法:对 `R_head · R_head_homeᵀ` 取旋转矢量。
- **同一条轨迹重复跑,头摆数字会差 15–119%**(Agent C 的噪声底),
  躯干倾角 3.11/3.16/**5.94**。所以比较头摆要用 ≥3 次的分布,不能看单次。
- **`hip_yaw` 的动作幅度跨 rollout 变化极大**(mean\|a\| 0.4 ~ 1.2,尾部到 10),
  所以基于它的惩罚项贡献会在 0.03~0.5/步之间浮动。
- `record_walk_angles.py --engine env` 用 `play=True`,推力每 0.5–1.0 s 一次,
  看起来像"一直在摔";`infer_policy.py` / `headless_eval.py` 用的是
  `scene.xml` 的位置致动器**不是 BAM**,不能用来评判策略。
